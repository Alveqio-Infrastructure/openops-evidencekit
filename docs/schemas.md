# JSON Schemas

OpenOps EvidenceKit publishes draft 2020-12 JSON Schemas for the primary
machine-readable artifacts:

- `schemas/evidence.schema.json`
- `schemas/report.schema.json`
- `schemas/report-history.schema.json`
- `schemas/executive-brief.schema.json`
- `schemas/evidence-drift.schema.json`
- `schemas/review-attestation.schema.json`
- `schemas/scorecard.schema.json`
- `schemas/scope-report.schema.json`
- `schemas/service-catalog.schema.json`
- `schemas/action-plan.schema.json`
- `schemas/gate-result.schema.json`
- `schemas/badge.schema.json`
- `schemas/policy-matrix.schema.json`
- `schemas/policy-coverage.schema.json`
- `schemas/questionnaire.schema.json`
- `schemas/inventory.schema.json`
- `schemas/privacy-scan.schema.json`
- `schemas/waivers.schema.json`
- `schemas/bundle-manifest.schema.json`
- `schemas/bundle-signature.schema.json`
- `schemas/bundle-verification.schema.json`
- `schemas/report-comparison.schema.json`

The bundled `validate` command uses a lightweight built-in validator so the CLI
does not need a JSON Schema dependency. The schema files are still useful for
editors, CI systems, documentation sites, and downstream tooling.

## Compatibility

Generated artifacts currently use `schema_version` `0.1`. Validators accept
`0.1` and patch-compatible versions such as `0.1.1`, but reject unknown
major/minor versions such as `0.2` or `1.0`. That keeps automation from silently
processing artifacts whose structure may have changed.

Patch-level schema versions may add optional fields. Removing required fields,
renaming fields, changing field types, or changing policy/report semantics must
use a new major/minor schema version and include a migration note.

## Evidence

Evidence files must contain:

- `schema_version`
- `generated_at`
- `metadata`
- `assets`
- `signals`

Signals intentionally allow extension fields so collector authors can add new
domains without waiting for a central schema update.

## Reports

Reports contain:

- `summary.score`
- `summary.status`
- `summary.checks_total`
- `summary.checks_passed`
- `summary.checks_failed`
- `summary.checks_warn`
- `results`

The report schema is stricter because it is generated by EvidenceKit and consumed
by automation. Each result entry must include stable machine fields: `id`,
`title`, `status`, `severity`, `required`, `path`, and `operator`.

## Report Histories

Report histories contain:

- `summary`
- `entries`

They are generated by `openops-evidence history append` and keep a compact
timeline of recurring report scores, status, failed checks, warnings, source
labels, and operator notes.

## Executive Briefs

Executive briefs contain:

- `summary`
- `top_findings`
- `next_steps`

They are generated by `openops-evidence brief report` and provide a compact,
deterministic readout for stakeholders who do not need the full technical report
format.

## Evidence Drift Reports

Evidence drift reports contain:

- `summary`
- `asset_changes`
- `domain_changes`

They are generated by `openops-evidence evidence diff` and compare two Evidence
JSON files. Asset changes include stable asset summary fields. Signal-domain
changes include structure summaries and SHA-256 fingerprints rather than raw
signal values.

## Review Attestations

Review attestations contain:

- `summary`
- `manifest`
- `checks`

They are generated by `openops-evidence attest review` and bind a review
statement to a manifest hash. Optional report, gate, scope, drift, and privacy
summaries become attestation checks.

## Scorecards

Scorecards contain:

- `summary`
- `domains`

They are generated by `openops-evidence scorecard report` and group check
results by evidence domain, such as backup, monitoring, access, TLS, docs, and
mail. Each domain records status, score, check counts, severity counts, and the
checks that contributed to the domain summary.

## Scope Reports

Scope reports contain:

- `summary`
- `assets`
- `domains`

They are generated by `openops-evidence scope report` and compare collected
evidence with a declared review scope. The report highlights missing in-scope
items, out-of-scope evidence that was collected anyway, and unclassified
evidence that lacks a scope declaration.

## Service Catalog Reports

Service catalog reports contain:

- `summary`
- `services`
- `unassigned_assets`

They are generated by `openops-evidence catalog report` and compare collected
evidence with a declared service catalog. Each service records owner,
criticality, contacts, expected assets, expected evidence domains, expected
runbooks, and missing items.

## Action Plans

Action plans contain:

- `summary`
- `items`

They are generated from report JSON and sort failed or warning checks into a
deterministic remediation queue. Each item includes a priority, check identity,
status, severity, source path, operator, observed count, waiver metadata, and
recommended action.

## Policy Matrices

Policy matrices contain:

- `summary`
- `checks`

They are generated from policy TOML/JSON and list the coverage contract for each
check: ID, title, evidence path, operator, expected value, severity, mode,
required flag, and remediation text.

## Policy Coverage

Policy coverage reports contain:

- `summary`
- `domains`

They are generated by `openops-evidence coverage report` from evidence and
policy input. The report shows which `signals.*` evidence domains are covered by
policy checks, which collected domains are not reviewed by policy, and which
policy domains are missing from the evidence input.

## Questionnaires

Questionnaires contain:

- `summary`
- `questions`

They are generated by `openops-evidence questionnaire policy` from policy files.
Each question records the check ID, evidence domain, severity, required flag,
evidence path, operator, expected value, and a plain request sentence that can be
sent to customers or internal system owners before a readiness review.

## Inventories

Inventories contain:

- `summary`
- `assets`
- `signal_domains`

They are generated by `openops-evidence inventory evidence` and provide a
compact, machine-readable asset and evidence-domain overview.

## Gate Results

Gate results contain:

- `summary`
- `conditions`

They are generated by `openops-evidence gate report` and record the exact CI
thresholds that were evaluated against a report.

## Badges

Badges contain:

- `schemaVersion`
- `label`
- `message`
- `color`

They are generated by `openops-evidence badge report` in the Shields.io endpoint
format so reports can expose a compact readiness status in README files, portals,
or documentation dashboards.

## Waivers

Waiver files contain:

- `waivers`

Each waiver records a `check_id`, `owner`, `reason`, and `expires_at` timestamp.
They can be authored as TOML or JSON. `schemas/waivers.schema.json` describes
the JSON shape, while `openops-evidence waiver validate` validates either TOML
or JSON inputs.

## Privacy Scans

Privacy scans contain:

- `summary`
- `findings`

They are generated by `openops-evidence privacy scan` before sharing artifacts.
Each finding records a file path, line number, finding kind, severity, and a
masked excerpt.

## Bundle Manifests

Bundle manifests contain:

- `metadata`
- `artifacts`

Each artifact entry records the display path, filename, inferred role, media
type, byte size, and SHA-256 hash. Manifests deliberately do not embed artifact
contents.

## Bundle Verifications

Bundle verifications contain:

- `summary`
- `results`

They are generated by checking manifest paths, file sizes, and SHA-256 hashes
against files on disk.

## Bundle Signatures

Bundle signatures contain:

- `metadata`
- `manifest`
- `signature`

They are detached HMAC-SHA256 signatures over the exact bundle manifest bytes.
The signature document records the manifest filename, byte size, SHA-256 hash,
algorithm, and signature value.

## Report Comparisons

Report comparisons contain:

- `summary`
- `regressions`
- `improvements`
- `neutral_changes`
- `added`
- `removed`

They are generated from two report JSON files and can be used as a CI guardrail
or as a compact change summary for recurring readiness reviews.
